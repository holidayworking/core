# Using Vite+, the Unified Toolchain for the Web

This project is using Vite+, a unified toolchain built on top of Vite, Rolldown, Vitest, tsdown, Oxlint, Oxfmt, and Vite Task. Vite+ wraps runtime management, package management, and frontend tooling in a single global CLI called `vp`. Vite+ is distinct from Vite, and it invokes Vite through `vp dev` and `vp build`. Run `vp help` to print a list of commands and `vp <command> --help` for information about a specific command.

Docs are local at `node_modules/vite-plus/docs` or online at https://viteplus.dev/guide/.

## Review Checklist

- [ ] Run `vp install` after pulling remote changes and before getting started.
- [ ] Run `vp check` and `vp test` to format, lint, type check and test changes.
- [ ] `vp check` only lints/formats code (Oxlint/Oxfmt). For Markdown content (e.g. `apps/zenn`, docs), also run root-level `pnpm lint` (cspell, markdownlint, textlint) and `pnpm fix` to autofix.
- [ ] Check if there are `vite.config.ts` tasks or `package.json` scripts necessary for validation, run via `vp run <script>`.
- [ ] If setup, runtime, or package-manager behavior looks wrong, run `vp env doctor` and include its output when asking for help.

## Running Commands

- If `vp` is not in PATH, use `node_modules/.bin/vp` from the repo root.
- To run a command scoped to a package: `vp exec --filter @<scope> <cmd>` (e.g., `vp exec --filter @infrastructures/aws cdk synth`).
- To update Vitest snapshots: `vp exec --filter @<scope> vp test -- --update`.

## Pull Requests

- Test Plan sections should only list manual verification steps. Omit anything already covered by CI (`vp check`, `vp test`, `cdk synth`/`cdk diff`, `nix flake check`, etc.).

## Package Naming

- Avoid bare names that collide with Node.js built-ins (e.g. `constants`, `path`, `fs`). Use scoped names like `@core/<name>` instead — with `moduleResolution: "nodenext"` and `@types/node`, TypeScript resolves bare built-in names to the Node.js type declarations rather than the workspace package.
- `vp check --fix` auto-sorts imports; no need to maintain import order manually.

## Architecture

This monorepo mixes two toolchains:

- JS/TS workspaces managed by Vite+ (`vp`): `apps/hugo` (Hugo static site), `apps/photo`, `apps/radicast`, `apps/zenn` (a Zenn articles/books repo), `infrastructures/aws` (`@infrastructures/aws`, shared AWS CDK), `packages/constants` (`@core/constants`), `packages/utils` (`@core/utils`). `apps/photo` and `apps/radicast` also have their own `cdk.json`/`bin/` — they're separate CDK apps, not just libraries.
- Nix system configuration under `nix/`: `nix/modules` (den modules, all auto-imported by import-tree; hosts are `aries`/`taurus` macOS, `gemini` an `aarch64-linux` NixOS laptop with GNOME, `cancer` an `aarch64-linux` NixOS server), `nix/packages`, `nix/patches`, `nix/sources`, `nix/secrets` (SOPS-encrypted; requires the age key from `~/.config/sops/age/keys.txt`, see README).

## Nix Modules

The configuration uses [den](https://den.denful.dev) on flake-parts. `flake.nix` is generated by flake-file: never edit it by hand. Declare inputs with `flake-file.inputs` next to the module that uses them, then run `nix run .#write-flake` and `nix flake lock`.

- Layout of `nix/modules`: `dendritic.nix` (flake-file and den wiring), `defaults.nix` (`den.default`: stateVersions, nixpkgs config and overlays, batteries, `base`), `hosts/<name>/default.nix` (`den.hosts` declaration plus host aspect, including the host's hardware config; keep each host to this one file), `user.nix` (user aspect, holding every personal value: user name, full name, email, SSH keys), `aspects/<group>/` (features), `flake-parts/` (`perSystem` outputs). Files whose path contains `/_` are not auto-imported; import them explicitly. Anything that isn't a flake-parts module (`nix/packages`, ...) must stay outside `nix/modules`.
- A host selects features by listing groups in its `includes`. There are no profiles or enable options. `base` reaches every host through `den.default`. Groups are flat: their files define `den.aspects.<group>` itself, so there is no list to keep. In a flat group, put a feature's settings in `aspects/<group>/default.nix`, and give it its own `<name>.nix` only if it declares `flake-file.inputs`, needs `let` bindings or helper derivations, contains a multi-line string (an embedded config file or script), or exceeds 20 formatted lines. Tools built around the same program share that file (e.g. `git.nix` also holds `gh`, `ghq`, `git-now`, `glab` and `tig`).
- An aspect only describes behaviour, never who uses it: write plain `nixos`, `darwin`, `os` and `homeManager` keys. `darwin`/`nixos` keys are ignored on other OSes, but `homeManager` keys are not, so make OS-specific Home Manager config conditional inside the value (`lib.mkIf pkgs.stdenv.hostPlatform.isLinux { ... }`), or, when it needs `imports`, hand it to `home-manager.sharedModules` in a `darwin`/`nixos` key (see `aspects/desktop/claude.nix`).
- Install macOS-only apps with nix-darwin in a `darwin` key: `environment.systemPackages` (copied to `/Applications/Nix Apps`), a nix-darwin `programs.<name>` module, or `programs.mas` for App Store apps. Install apps used on both Linux and macOS with a Home Manager `programs.<name>` module in a `homeManager` key when one exists, otherwise with `environment.systemPackages` in an `os` key.
- For `{ user, ... }:` or `{ host, ... }:` context, write the aspect itself as a function: in a flat group, a file can define `den.aspects.<group> = { user, ... }: { ... };` and den merges it with the group's other files (see `aspects/desktop/1password.nix` and `aspects/desktop/xremap.nix`). Don't put anonymous functions in `includes`. In darwin modules, read the primary user from `config.system.primaryUser` (set by the `primary-user` battery) instead of using a parametric aspect.
- den drops config silently, so check where it lands ([docs](https://den.denful.dev/explanation/where-config-lands/)) and confirm with `nix eval` when adding a new delivery path:
  - `homeManager` keys reach the user from a host's `includes` only through the `host-aspects` battery on `den.aspects.hidekazu`. `den.schema.host.includes` is dropped even with that battery; use `den.default.includes` for everything global.
  - Don't write `nixos`/`darwin`/`os` keys directly on a user aspect ([#694](https://github.com/denful/den/issues/694)); use `provides.to-hosts`.
- Unfree packages are allowed globally (`nixpkgs.config.allowUnfree` in `defaults.nix`); don't use `den.batteries.unfree`.
- Module function arguments follow this order: `den, inputs, lib, pkgs, config, ...` (include only what's actually used). Inside class modules (`homeManager = { config, ... }: ...`) `config`, `lib` and `pkgs` are normal module arguments, and `imports` works.
- Order and separate elements in a module as follows:
  - Top level of a file: `flake-file.inputs`, then the aspect definition (`den.aspects.<group>`).
  - Aspect keys: `includes`, `os`, `nixos`, `darwin`, `homeManager`.
  - Class modules: `imports` first, then options alphabetically.
  - Option attributes: `enable`, then the option's basic settings (`package`, `shell`, `defaultKeymap`), then the rest alphabetically.
  - `flake-file.inputs` entries: `url`, then `inputs.*.follows`.
  - Lists: alphabetically, unless the order is meaningful (e.g. command arguments such as an MCP server's `args`).
  - Blank lines: separate every entry at the top level of a file, in an aspect and at the top level of a class module. Inside an option, keep consecutive scalar values together, and separate a list or attribute set (even on one line, such as `[ ... ]` or `{ }`) or a multi-line string from its siblings with blank lines.
  - Exception: `starship.settings` in `aspects/base/zsh.nix` follows the prompt segments in `format`, with no blank lines between them.
- To apply Nix changes: `make nix/build` (dry build) or `make nix/switch` (build + activate), both via `scripts/nh.sh`, which runs `nh os` on Linux / `nh darwin` on macOS for the current host (`$HOSTNAME`), or `nh os` against a remote host when `TARGET_HOST` is set. Initial macOS setup only: `make darwin/setup HOST=<name>` (`HOST` is required; hostname isn't configured yet at that point) — see README.md.
